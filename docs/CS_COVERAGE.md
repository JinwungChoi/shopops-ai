# 고객 문의 경우의 수 표

Style Shop 채팅에서 고객이 할 수 있는 요청을 영역 × 동작으로 나누고, 칸마다 처리 방식을 정했다. 빈칸은 없다. 각 칸은 다음 넷 중 하나로 처리한다.

- **도구**: 서버 도구가 DB에서 조회하거나 확인 카드를 만든다. 실제 변경은 고객이 카드에서 확인할 때만 일어난다.
- **정책**: 등록된 정책 문서를 검색해 출처와 함께 답한다. 근거가 없으면 보류한다.
- **상담 연결**: 채팅에서 처리하지 않고 상담 문의 확인 카드를 띄운다.
- **불가 안내**: 채팅에서 확인하거나 처리할 수 없다고 말하고 상담원 연결 방법을 안내한다. 비슷한 도구로 다른 질문에 답하지 않는다.

시나리오 ID는 `scripts/cs-scenarios.mjs`에 있고, 기대 결과가 적힌 시나리오(G로 시작)는 실행 후 자동 채점된다.

## 권한과 실행 원칙

- 고객 의도와 다음 도구는 모델이 고르고, 업체·고객 범위와 판정은 서버와 DB가 정한다.
- 확인 없이 실행되는 쓰기는 장바구니(본인, 수량 1~10, 재고 이내, 되돌릴 수 있음)뿐이다. 주문·취소·배송지 변경·교환·반품·상담 문의는 고객이 카드에서 확인해야 실행된다.
- 조회 도구가 없는 요청에 비슷한 도구로 답하지 않는다. `finish(unsupported)`로 불가 안내를 한다.

## 검증 (2026-11-25, 로컬, 실제 모델)

- 전체 100개 시나리오 실행, 그중 기대 결과가 있는 G 시나리오 39개 자동 채점: 39개 통과. 교환 시나리오가 실패했던 것은 이전 실행이 L 재고를 소진했기 때문이었다. `seed-catalog`로 재고를 되돌린 뒤 다시 실행해 통과를 확인했다.
- DB 테스트(pgTAP) 125개 통과. 접수 내역·주문 상세 RPC가 다른 고객과 다른 업체를 막는지, 고객과 익명 사용자가 직접 실행할 수 없는지 확인한다.
- 데모 고객 A·B에는 이미 접수된 반품과 상담 문의가 시드돼 있어 "반품 신청건"과 "문의 내역"이 빈 결과로 끝나지 않는다. 공개 데모의 매일 초기화 스냅샷에 포함된다.
